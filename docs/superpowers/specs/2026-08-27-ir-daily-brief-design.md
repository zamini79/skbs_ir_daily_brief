# IR Daily Brief 자동화 — 설계 문서

작성일: 2026-08-27
상태: 데이터 소스 전 항목 실측 완료 / 구현 계획 대기

## 1. 목적

IR팀이 매일 아침 전 임원·전 팀장에게 발송하는 Daily Brief 메일의 본문을,
담당자 출근 시각(평일 08:00 KST) 이전에 자동으로 수집·작성해 둔다.
담당자는 뉴스와 요약문을 고르기만 하면 된다.

## 2. 산출물

첨부 샘플(`IR_Daily_Brief_sample.xlsx`)과 동일한 표를 생성한다.

| 구분 | 기업 | 주가 | 전일대비 | % | 연초대비 | 시가총액(조원) | 뉴스 |
|---|---|---|---|---|---|---|---|

- 구분·기업은 고정값(총 23행): 국내사 10 / 해외사 9 / Index 4
- 뉴스 칸은 2행 병합 구조: 1행 = 기사 제목(+링크), 2행 = 요약문
- Index 행의 시가총액은 `-`
- 해당 기업 뉴스가 없으면 뉴스 칸은 공란

## 3. 데이터 소스

08:00 KST는 국내장 개장(09:00) 전이므로, 모든 시세는 **전영업일 종가** 기준이다.
실시간 시세가 필요 없다는 점이 무료 티어 선택지를 넓힌다.

**더 정확히는, 브리프가 원하는 값은 실행 시각과 무관해야 한다** — "직전 영업일 종가와
그 전 영업일 대비". 같은 날 07:40 에 돌리든 10:30 에 다시 돌리든 같은 표가 나와야 한다.
이 요구를 소스에서 그냥 받아 낼 수 있다고 가정했다가 §3.0 의 결함이 생겼다.

### 3.0 ★ 네이버 `basic` 의 전일대비는 "오늘 지금까지"다 — 우리가 원하는 값이 아니다 (2026-08-31, Task 35)

**국내 11행 전부가 「전일대비 0」인 브리프를 매일 아침 만들고 있었다.**

`m.stock.naver.com/.../basic` 의 `compareToPreviousClosePrice` 는 이름과 달리
"직전 영업일 대비"가 아니라 **"오늘 지금까지의 변동"**이다. 개장 전에는 오늘이 아직
움직이지 않았으니 당연히 0 이고, `localTradedAt` 은 그래도 **오늘 날짜**로 온다.
실측(2026-08-31 08:56 KST, 개장 4분 전):

    302440  closePrice "38,950"  compareToPreviousClosePrice "0"  fluctuationsRatio "0.00"
            localTradedAt "2026-08-31T08:56:56+09:00"
    KOSPI   closePrice "6,788.88" compareToPreviousClosePrice "0.00"
            localTradedAt "2026-08-31T08:56:56+09:00"

`closePrice` 38,950 은 **금요일 종가로 맞다.** 틀린 것은 변동값(0)과 기준일(오늘)
둘이다. 기준일이 오늘이라 화면은 **금요일 가격에 「기준 2026-08-31」을 붙였다.**
`integration` 의 `lastClosePrice` 도 뜻이 같아서("오늘 기준의 전일") 개장 전에는
`closePrice` 와 같은 값이 온다 — 뺄셈으로 구하든 그 필드를 쓰든 똑같이 0 이 된다.

크론은 **07:40 KST** 다. 즉 정기 실행은 매일 아침 이 상태를 만났고, 담당자는
"오늘 아무 종목도 안 움직였다"고 읽게 된다. 실제 금요일에는 SK바이오사이언스가
+500(+1.30%), 삼성바이오로직스가 −108,000(−6.78%) 움직였다.

**해결: 항상 일별 시세 계열에서 뽑는다.** `api.finance.naver.com/siseJson.naver` 는
연초 기준가(§3.5)가 이미 쓰던 엔드포인트이고, 마지막 두 행이 정확히 우리가 원하는
값이다 — 마지막 행 종가 = 주가, 그 앞 행 종가 = 전일 종가, 마지막 행 날짜 = `asOf`.
KOSPI 도 같은 엔드포인트가 정상 응답한다(`symbol=KOSPI`).

**시각으로 분기하지 않는다.** "09:00 전이면 계열을 쓴다" 같은 코드는 휴장일·반휴장·
연휴에서 다시 틀린다. 항상 계열에서 뽑으면 실행 시각과 무관하게 같은 값이 나온다.

#### 계열도 그냥 쓰면 안 된다 — 장중에는 오늘 행이 붙는다

**"마지막 두 행"을 그대로 쓰면 결함이 방향만 바꿔 되돌아온다.** 계열은 장중에
**진행 중인 오늘 행**을 붙인다(실측 2026-08-31 09:05, 개장 5분 뒤):

    ["20260828", 38300, 38950, 38000, 38950, 57833, 5.97]
    ["20260831", 38450, 38450, 37650, 37700,  2612, 5.97]   ← 거래량 2,612, 진행 중

마지막 행의 "종가" 자리에는 그 순간의 현재가가 들어온다. 그 행을 쓰면 07:40 브리프는
+500(+1.30%), 09:05 재수집은 −1,250(−3.21%) 이 되어 **같은 날 같은 브리프의 숫자가
달라진다.**

그래서 **KST 오늘 날짜의 행은 무조건 버린다.**

**장 마감 뒤(16:00)에도 버린다.** 이건 아침 브리프이고, **날짜 D 의 브리프는 언제
수집하든 D-1 종가를 보여야 한다.** 마감 후에만 오늘 행을 받아들이면:

- 담당자가 검토·확정한 가격과 **보관된 브리프가 달라진다.** 메일이 이미 나갔으면
  아카이브가 발송본과 어긋난다.
- 같은 날짜를 다시 돌렸을 때 다른 답이 나온다 — **그게 정확히 이번 결함의 성질이다.**

"직전 영업일"을 마감 후에는 오늘로 읽을 여지가 있다는 지적은 맞지만, 그건 **저녁
브리프라는 다른 제품**이다. 필요해지면 그때 별도로 만든다. **이 규칙을 되돌리지 마라.**

시각이 아니라 **날짜**로 거르므로 09:00·15:30 같은 장 시간 상수를 코드가 알 필요가
없고, 반휴장(조기 마감)도 저절로 맞는다.

거래일이 하루뿐이면(신규 상장) **전일대비를 지어내지 않고 실패로 남긴다.**

#### 다른 소스는 이 함정에 걸리지 않는다 (전부 실측, 2026-08-31 08:56 개장 전)

| 소스 | 개장 전 상태 | 판정 |
|---|---|---|
| `naver-index` `.INX`/`.IXIC` | `localTradedAt 2026-08-28`, 변동 −19.23 / −138.93 | **정상** — 미국장이 마감해 "오늘"이 곧 그 시장의 마지막 세션이다 |
| `naver-world-stock` (2269.HK) | `localTradedAt 2026-08-28T16:00+08:00`, 변동 0.150 | **정상** — 홍콩 개장(10:30 KST) 전인데도 직전 세션 값을 준다 |
| `lse` (GSK) | `lastclosedate 2026-08-28`, `netchange 1.5` | **정상** |
| `six` (LONN) | `MarketDate 20260828`, Closing 583.8 / Previous 588.4 | **정상** |
| `twelvedata` 미국 5종목 | `datetime 2026-08-28`, `is_market_open false` | **정상** |
| `krx` 코스피200 헬스케어 | 마지막 게시일 기준 | **정상** |

즉 이 결함은 **국내 네이버 경로 하나에만** 있었다. 국내 시장만 우리 실행 시각과
같은 시간대에 있어서, "오늘"이 아직 시작도 안 한 상태를 우리만 마주쳤기 때문이다.

#### KRX 경로도 같은 규칙으로 맞췄다 (Task 35 후속)

`fetchKrxIndexQuote` 는 KST 오늘부터 거슬러 올라갔다. 개장 전에는 오늘치가 없어(실측:
09:25 에도 `basDd=20260831` 은 0행) 07:40 결과가 옳았지만, **KRX 가 장 마감 후 당일치를
게시하면 그때부터는 이 한 행만 오늘 날짜를 집었다** — 나머지 22행이 금요일 기준인데
코스피200 헬스케어만 월요일이 되어 표 안에서 기준일이 어긋난다.

지금은 **어제부터** 거슬러 올라간다. 실측 확인(2026-08-31, 실제 KRX API):
`now = 2026-08-28 23:00 KST`(그날치 51행이 이미 게시된 시점)로 불러도 `asOf` 가
`2026-08-27` 로 나온다 — 오늘 행을 집지 않는다.

연초 기준가(`fetchKrxIndexYtdBase`)는 전년 12/31 부터 찾으므로 이 규칙과 무관하다.

#### 호출량과 속도 제한

국내 종목은 세 곳(계열 + `basic` + `integration`)을 부른다. 전에는 두 곳(`basic` +
`integration`)이었으므로 종목당 한 번 늘었고(시총 되계산에 현재가가 필요하다), KOSPI 는
시총이 없어 **한 번**으로 줄었다. 하루 21회 → **31회**다.

**속도 제한은 실측으로 확인했다** — 뉴스 쪽에서 한 번 물린 적이 있어(§2.7 운영 문서의
`NEWS_CONCURRENCY = 1`) 시세 쪽도 같은 종류가 있는지 봐야 했다. 계열 엔드포인트에
11 → 22 → 22 회를 연속 동시 요청했고 **55회 전부 HTTP 200, 스로틀 없음**이었다
(2026-08-31 08:58). 키가 없고 한도 관리 대상도 아니다(§3.2 의 네이버 국내 경로와 같다).

#### 시가총액도 거래일 종가 기준으로 되계산한다 (Task 35 후속)

`integration.totalInfos.marketValue` 는 **그 순간의 현재가로 계산된 값**이다.
실측(2026-08-31, 302440):

    08:58 (개장 전)  현재가 38,950   marketValue "3조 559억"
    09:19 (장중)     현재가 37,950   marketValue "2조 9,813억"

그대로 쓰면 장중·마감 후 재수집에서 **주가는 금요일인데 시총만 오늘 장중** 값이 되어
한 행 안에 두 시점이 섞인다. 73조짜리가 1% 움직이면 0.73조라 화면에 그대로 보인다.

그래서 **응답에서 주식 수를 역산해 거래일 종가로 다시 곱한다**:

    주식 수   = marketValue / 그 응답 시점의 현재가
    시가총액  = 주식 수 × 우리가 고른 거래일 종가

시드에 `sharesOutstanding` 을 넣지 않는다(§3.4). 국내 종목은 분기마다 손으로 갱신해야
하고, 역산하면 유상증자·자사주 소각이 저절로 따라온다.

**현재가는 `basic.closePrice` 에서 온다.** `integration` 에는 현재가가 없다(실측:
`totalInfos` 에 `lastClosePrice`·`openPrice`·`highPrice`·`lowPrice` 는 있어도 현재가는
없고, `dealTrendInfos[0]` 은 현재가가 아니라 **직전 거래일** 종가다). 그래서 국내 종목의
호출은 세 곳(계열 + `basic` + `integration`)이 됐다 — 이 되계산의 유일한 비용이다.

**한계**: 두 값이 서로 다른 응답에서 오므로 장중에는 표본 시각이 조금 어긋난다. 실측으로
역산 주식 수가 78,456,996(08:58) 대 78,558,630(09:19)으로 **약 0.13%** 차이났다. 그래도
아무것도 안 했을 때의 오차(위 예에서 2.4%)보다 한 자릿수 작고, **개장 전에는 현재가 =
직전 종가라 오차가 0 이다** — 07:40 정기 실행에서 이 되계산은 값을 바꾸지 않는다.
바로잡는 대상은 어디까지나 장중·마감 후 재수집이다.

현재가가 없거나 0 이면 **역산하지 않고 시총만 비운다.** 지어내지 않는다.

**두 엔드포인트의 실패는 다르게 다룬다**: 시세가 실패하면 그 종목은 실패다.
시총만 실패하면 **시세는 살리고** 시총 칸만 비우되, 사유를 로그에 남긴다
(`[quote] {code}: 시가총액 조회 실패 …`) — 시총 공란은 화면에서 지수 행과 구분되지
않아 로그가 없으면 몇 주째 죽어 있어도 아무도 모른다.

### 3.1 탈락시킨 후보와 이유

- **Yahoo Finance**: 429 Too Many Requests 즉시 발생, 쿨다운 후에도 동일. ToS 회색지대.
- **Stooq CSV**: 엔드포인트 폐쇄 확인.
- **Google Sheets GOOGLEFINANCE**: 과거 시세가 Sheets API/Apps Script에서 `#N/A` →
  연초대비 계산 불가. 국제 거래소 대부분 미지원. ToS의 professional-use 금지 조항.
- **네이버 해외주식**: 공개 API 경로 없음. 런던·파리·취리히 미지원.

### 3.2 해외 비미국 4종목 — 소스 4개로 분리 (marketstack 한도 회피)

Twelve Data 무료 플랜은 비미국 상장을 전부 차단하므로 marketstack을 병용한다.
심볼 형식이 관건이었다. MIC 접미사(`GSK.XLON`)는 뉴욕 ADR 가격을 XLON 라벨로
잘못 반환했고, **거래소 약칭 접미사**가 정확했다.

> 아래 표는 **그 최초 조사의 기록이다(2026-08-27).** 지금 매일 도는 시세는 이 중
> 사노피 한 종목만 marketstack 을 쓴다(호출량 절 참조). 표를 남겨 두는 이유는
> 두 가지다: **① 비미국 4종목의 값이 샘플 엑셀과 맞는지 실제로 대조했다는 기록**이고,
> **② MIC 접미사 함정**은 marketstack 을 다시 쓸 때 똑같이 되풀이될 문제다.
> 사노피 심볼(`SAN.PA`)과 네 종목 전부의 **연초 기준가 심볼**이 지금도 이 표를 따른다.

| 종목 | 심볼 | 실측 종가 | 샘플 엑셀 | 판정 |
|---|---|---|---|---|
| GSK | `GSK.L` | 1,890.5 GBP (XLON) | GBP 1,905.5 | 일치 (일자 차이) |
| Sanofi | `SAN.PA` | 78.74 EUR (XPAR) | EUR 79.74 | 일치 (일자 차이) |
| Lonza | `LONN.SW` | 593.8 CHF (XSWX) | CHF 593.8 | **완전 일치** |
| Wuxi | `2269.HK` | 52.2 HKD (XHKG) | HKD 52.2 | **완전 일치** |

HTTPS는 무료 플랜에서 정상 동작한다(v2 실측). HTTP 전용이라는 통설은 사실이 아니다.

**주의 1 — 런던은 펜스 호가다.** `GSK.L`의 1,890.5는 GBP가 아니라 GBX(펜스)이며
실제로는 £18.905다. marketstack은 `price_currency`를 `GBP`로 표기하므로 그대로 믿으면
시가총액이 100배가 된다. 검산: £18.905 × 발행주식 약 40억 × GBP/KRW ≈ 142조로
샘플의 145.4조와 부합한다. **표시 가격은 펜스 그대로, 시총 계산 시에만 100으로 나눈다.**
`Instrument.priceDivisorForMarketCap` 필드로 종목별 보정값을 둔다(GSK만 100, 나머지 1).

**주의 2 — 국제 시장 데이터에 지연이 있다.** 실측 시 미국(AAPL)은 08-26 종가였으나
`GSK.L`은 08-24였다. 최신 영업일이 아닐 수 있으므로 응답의 `date`를 반드시 저장하고,
검수 화면에 시세 기준일을 함께 표시해 담당자가 판단할 수 있게 한다.
(거래소 직접 조회로 옮긴 3종목은 이 지연이 없어졌다 — 2026-08-28 실측에서 셋 다
전영업일 종가였다. 그래도 기준일 저장·노출 규칙은 그대로 유지한다. 소스가 무엇이든
거래일이 국내와 다를 수 있다는 사실은 변하지 않는다.)

**호출량 — 초안의 「월 22회」는 틀렸다. 실제로는 월 88회였다.**

marketstack 무료 플랜은 **호출 수가 아니라 심볼 수**로 센다(그들의 FAQ: 요청에 티커
5개가 들어 있으면 5회가 소비된다). 4종목을 콤마로 묶어도 한 번에 4회가 빠져나가므로
4종목 × 22거래일 = **월 88회**이고 한도는 100이다. 마진이 사흘치뿐이라 재시도 한 번,
수동 재수집 한 번이면 넘긴다. **2026-08-27 에 실제로 소진됐다**:

    HTTP 429  {"error":{"code":"usage_limit_reached",
                        "message":"Your monthly usage limit has been reached."}}

**이후 한도 문제로 3종목을 이관했다(2026-08-28).** 매일 도는 시세만 각 거래소가 자기
화면에 쓰는 무료 엔드포인트로 옮기고, **연 1회짜리 연초 기준가는 네 종목 모두
marketstack 에 남긴다**(연 1회 조회 후 `YtdBasePrice` 캐시).

| 종목 | 시세 소스 | 심볼 | marketstack 소비 |
|---|---|---|---|
| GSK | **LSE 공식 엔드포인트** `api.londonstockexchange.com` | `GSK` | 0 |
| Sanofi | marketstack (그대로) | `SAN.PA` | 월 22 |
| Lonza | **SIX 공식 엔드포인트** `www.six-group.com/fqs` | `LONN` | 0 |
| Wuxi | **네이버**(이미 쓰는 소스) `api.stock.naver.com/stock/2269.HK/basic` | `2269.HK` | 0 |

결과: 월 88회 → **월 22회 + 연 3~4회.** 마진 78.

**심볼 표기가 소스마다 다르다**(`GSK.L`→`GSK`, `LONN.SW`→`LONN`, `2269.HK` 는 그대로).
연초 기준가는 여전히 marketstack 이므로 `src/providers/quote/ytdBase.ts` 의
`MARKETSTACK_YTD_SUFFIX` 가 조회 직전에 접미사를 되붙인다. **여기가 이 구성에서 가장
조용히 깨지기 쉬운 지점이다** — 되붙이지 않으면 marketstack 이 오류가 아니라 빈 응답을
주고 연초대비 칸만 사유 없이 빈다.

**사노피의 1차를 marketstack 으로 남긴 이유.** 유로넥스트의 ajax 응답이 암호화된
블롭(`ct:`)이라 직접 쓸 수 없다. **사노피용 1차 소스를 새로 만들지 마라.**

#### 폴백: 1차가 실패한 날에만 부르는 2차 소스 (2026-08-28, Task 32)

위 표의 소스는 **하나가 죽으면 그 행이 하루 종일 빈다.** 실제로 사노피는 marketstack
월 한도가 소진돼 다음 달까지 매일 실패하는 상태였고, 나머지 셋도 비문서화 엔드포인트라
예고 없이 바뀔 수 있다(§13 리스크 4). 그래서 **네 종목 모두에 2차 소스를 붙였다.**

| 종목 | 1차 | 2차 | 2차 심볼 |
|---|---|---|---|
| GSK | lse | **ft** | `GSK:LSE` |
| Sanofi | marketstack | **ft** | `SAN:PAR` |
| Lonza | six | **ft** | `LONN:SWX` |
| Wuxi | naver-world-stock | **ft** | `2269:HKG` |

설정은 시드에 있다(`Instrument.quoteFallbackSource`/`quoteFallbackSymbol`, 둘 다 nullable).
배선은 `src/providers/quote/index.ts` 의 폴백 단계이고, 파서는 `src/providers/quote/ft.ts` 다.

**왜 FT 를 2차에만 두는가.** FT 는 JSON API 가 아니라 **사람이 보는 HTML 페이지를 긁는다** —
지금 쓰는 어떤 소스보다 취약한 의존이다. LSE·SIX·네이버도 비문서화 엔드포인트지만 적어도
기계용 JSON 이라 필드가 바뀌면 바뀐 티가 난다. HTML 은 배너 하나, 광고 한 줄로도 구조가
변한다. 그래서 **평소에는 아예 부르지 않고**(1차가 성공하면 2차 호출은 0회), 1차가 실패한
날에만 부른다. 넷을 한 소스로 덮을 수 있다는 것이 FT 의 유일한 장점이고, 그 장점은 2차
자리에서도 그대로 얻는다. **FT 를 1차로 올리지 마라.**

파싱 규칙(실측 2026-08-28):

    GET https://markets.ft.com/data/equities/tearsheet/summary?s=SAN:PAR
    → <span class="mod-ui-data-list__label" …>Price (EUR)</span>
      <span class="mod-ui-data-list__value">77.28</span>
      <span class="…__label" …>Today's Change</span>
      <span class="…__value"><span class="mod-format--neg"><i…></i>-1.01 / -1.29%</span></span>
      <div class="mod-disclaimer">Data delayed at least 15 minutes, as of Aug 27 2026 16:39 BST.</div>

- **위치나 순서가 아니라 라벨 텍스트로 찾는다.** 순서로 읽으면 FT 가 항목 하나를 옮긴 날
  종가 자리에 거래량이나 베타가 들어오고, 값이 그럴듯한 숫자라 아무도 눈치채지 못한다
  (SIX 의 `colNames` 인덱싱과 같은 이유).
- 통화는 `Price (XXX)` 괄호 안이다. 네 통화 전부 실측 확인했다(GBX·EUR·CHF·HKD).
  **GSK 는 FT 에서도 GBX(펜스)로 온다** — 주의 1 의 `priceDivisorForMarketCap = 100` 이
  폴백 경로에서도 그대로 맞는다.
- 전일 종가 = `가격 − 변동금액`(`/` 앞). 검산: 77.28 − (−1.01) = 78.29.
  **등락률(`/` 뒤)은 버린다** — 전 종목을 `domain/calc.ts` 로 계산한다.
- **라벨을 못 찾으면 실패다.** 0 이나 null 로 채우지 않는다. 폴백 경로는 평소에 아무도
  보지 않으므로, 조용히 0원이 찍히면 그 상태가 몇 주 간다.
- `asOf` 는 시세 모듈의 데이터 기준 시각(런던 시간)에서 읽는다. 네 거래소(런던·파리·
  취리히·홍콩)의 장 시간이 모두 **런던 달력 날짜 안에서 끝나므로** 그 날짜가 곧 거래일이다.
  기준 시각이 없거나 페이지 안에서 서로 어긋나면 **빈 값으로 두고 화면이 「기준일 미상」이라
  말하게 한다** — 날짜를 추측해 채우지 않는다.
- 없는 심볼은 오류가 아니라 **302 리다이렉트**다(`LONN:VTX` → `/data/search?…`, 실측).
  따라가면 종목 페이지가 아닌 곳의 숫자를 읽게 되므로 따라가지 않고 실패로 남긴다.

**폴백은 실패를 없애지 않는다.** 1차와 2차가 함께 죽으면 그 행은 지금처럼 「시세 실패」로
뜨고, 사유에는 **두 소스의 실패 이유가 모두** 실린다(`{1차 사유} | 폴백(ft) 실패: {2차 사유}`).
값을 지어내거나 어제 값을 재사용하지 않는다.

**폴백이 돌면 그 사실이 드러나야 한다.** 값이 채워지므로 실패처럼 보이지 않는 것이 이
장치의 가장 큰 위험이다 — 표시가 없으면 1차가 몇 주째 죽어 있어도 아무도 모른다. 세 군데에
남긴다: ① 그 행의 「ft 대체」 배지(주가 칸), ② `[quote] … 1차(…) 실패로 2차(…)를 썼다` 로그,
③ 크론 응답의 `quoteFallbackUsed` 카운터. **배너(`BriefRun.status`)는 흔들지 않는다** —
값을 얻은 실행이므로 PARTIAL 이 아니다(그렇게 하면 배너가 뜻을 잃는다).

**연초 기준가는 폴백과 무관하다.** FT 에는 과거 데이터가 없다. 네 종목의 기준가는 지금처럼
marketstack 경로를 그대로 쓴다(`ytdBase.ts` 는 `quoteSource` 로만 라우팅하므로 폴백 필드가
그 배선에 닿지 않는다).

**새 엔드포인트 실측 (2026-08-27 조사, 2026-08-28 재확인. 전부 키 불필요).**

    GET https://api.londonstockexchange.com/api/gw/lse/instruments/alldata/GSK
    → currency "GBX", lastclose 1852, netchange -47.5, percentualchange -2.500658…,
      lastclosedate "2026-08-27T15:35:27.000"

- **전일 종가는 그대로 오지 않는다. `lastclose - netchange` 로 구한다** → 1899.5.
  검산: −47.5 / 1899.5 = −2.5007% 로 `percentualchange` 와 일치한다.
  `previousclose`·`closeprice`·`tradingdate` 는 **null 이다. 쓰면 안 된다.**
  `previousreferenceprice`(1899.5)도 오지만 배당락 조정 기준가일 수 있어 쓰지 않는다.
- 통화가 **GBX(펜스)**로 온다 — 주의 1 그대로다. 표시는 펜스, 시총만 100 으로 나눈다.

    GET https://www.six-group.com/fqs/ref.json
        ?select=ClosingPrice,PreviousClosingPrice,MarketDate,Currency&where=ValorSymbol=LONN
    → colNames ["ClosingPrice","PreviousClosingPrice","MarketDate","Currency"],
      rowData [[588.4, 587.8, 20260827, "CHF"]], totalRows 1, delayMinutes 15

- **`rowData` 는 값만 담은 배열이다. 위치가 아니라 `colNames` 로 인덱스를 찾는다** —
  select 순서가 바뀌면 종가와 전일 종가가 조용히 뒤바뀐다.
- `totalRows` 가 1 이 아니면 실패로 다룬다(없는 심볼은 오류가 아니라 `totalRows: 0`).
- 없는 필드명을 select 하면 **HTML 오류 본문**이 온다
  (`Invalid name 'ClosingDate' in select parameter`, 실측 HTTP 400). JSON 파싱 실패도 실패로 다룬다.
  `ClosingDate`·`LastTradedDateTime` 은 없는 이름이다 — `MarketDate` 를 쓴다.
- 15분 지연은 무관하다(07:40 KST 실행 시 취리히는 이미 마감). 값 교차 검증: SIX 588.4 = FT 588.40.

    GET https://api.stock.naver.com/stock/2269.HK/basic
    → closePrice "50.500", compareToPreviousClosePrice "-0.250",
      currencyType.code "HKD", localTradedAt "2026-08-27T16:00:00+08:00"

- **값이 문자열이다.** 기존 네이버 파서와 같은 규칙으로 숫자화한다.
  전일 종가 = `closePrice - compareToPreviousClosePrice`.
- `asOf` 는 `localTradedAt` 앞 10자다. **`new Date()` 로 파싱하지 않는다** —
  타임존이 KST 로 옮겨지며 날짜가 밀린다.
- `GSK.L`·`SAN.PA`·`LONN.SW` 는 네이버에 없다(HTTP 409 `Not Exist Master`).
  접미사 없는 `GSK`·`SAN` 은 **미국 ADR 이라 값이 다르다. 쓰면 안 된다.**

**등락률은 네 소스 중 어느 것에서도 받아 쓰지 않는다.** 전 종목을 `domain/calc.ts` 의
`changePct` 로 계산한다 — 소스별 반올림 규칙이 다르면 그 행만 끝자리가 어긋난다.

무료 한도 요약(다른 소스): Twelve Data 일 800회·분당 8크레딧, **KRX Open API 일 10,000회**,
네이버 검색 API 일 25,000회. KRX 실사용은 하루 1~2회(휴장일이면 거래일을 찾느라 최대 10회)
+ 연 1회 기준가 조회이므로 한도의 0.1% 도 쓰지 않는다.

### 3.3 코스피200 헬스케어 — KRX Open API 로 해결

**이 행은 자동 수집한다.** 처음에는 자동 소스가 없다고 판단해 수기 입력으로 남기기로
했으나(아래 폐기된 결론), 사용자가 "KRX 에 있는 지수"라고 알려줘 다시 찾았고
**KRX Open API 에 있음을 실측으로 확인했다.**

    GET https://data-dbg.krx.co.kr/svc/apis/idx/kospi_dd_trd?basDd=YYYYMMDD
    헤더: AUTH_KEY: <KRX_AUTH_KEY>,  Accept: application/json

- **HTTPS 필수.** http 는 리다이렉트로 빠진다.
- 무료. **하루 10,000회.** 2010-01-04 이후 데이터.
- 응답은 `OutBlock_1` 배열이고 하루치 KOSPI 계열 지수 전체다(실측 51행).
  우리 행은 `IDX_NM === '코스피 200 헬스케어'` 로 골라낸다.
- **모든 값이 문자열이다.** `Number()` 변환 후 `Number.isFinite` 로 검증한다.

| 실측(2026-08-27) | 결과 |
|---|---|
| `basDd=20260826` | 51행, 종가 2173.53, 전일대비 65.33 |
| `basDd=20251230` | 51행, 종가 2392.04, 전일대비 -6.67 |
| `basDd=20251231` | **0행** (국내 증시 연말 휴장) |
| `basDd=20260827` | **0행** (당일 마감 전 — 저녁에 조회해도 없다) |

**표기 함정.** KRX 는 `'코스피 200 헬스케어'`(코스피와 200 사이 공백 있음)라 쓰고,
우리 `Instrument.name` 은 원본 브리프 엑셀을 따라 `'코스피200 헬스케어'`(공백 없음)다.
이름으로 매칭하면 51행 중 아무것도 걸리지 않는다. 매칭 문자열은
`src/providers/quote/krx.ts` 의 `KRX_IDX_NM_KOSPI200_HEALTHCARE` 상수이고,
`Instrument.quoteSymbol` 이 이 값과 같은지는 테스트가 고정한다.

**휴장일은 오류가 아니라 빈 배열이다.** 잘못된 날짜 문자열도 똑같이 빈 배열이므로
"빈 응답"만으로는 휴장인지 오타인지 구분되지 않는다. 그래서 기준일부터 하루씩
거슬러 올라가되 **10일 상한**을 두고, 상한에 걸리면 조용히 비우지 않고 실패로 남긴다.
HTTP·인증 오류는 휴장과 구분해 즉시 던진다(401 을 휴장처럼 취급하면 10번 재시도한 뒤
엉뚱한 사유가 남는다).

**등락률은 우리가 계산한다.** 응답의 `FLUC_RT` 를 쓰지 않는다 — 등락률은 전 종목을
`domain/calc.ts` 의 `changePct` 로 동일하게 계산하고 있고, KRX 의 반올림 규칙이 다르면
이 한 행만 끝자리가 어긋난다. `prevClose` 는 `종가 - CMPPREVDD_IDX` 로 얻는다.

**시가총액은 비워 둔다.** 응답에 `MKTCAP` 이 오지만 원본 브리프 엑셀은 지수 행의 시총
칸을 `-` 로 비우고, 다른 지수 3행도 그렇다.

**시세 기준일이 하루 늦을 수 있다.** KRX 는 당일 마감 후에도 그날 행을 바로 주지 않는다
(실측: 20260827 저녁에도 0행). 07:40 정기 실행은 어차피 전영업일 기준이라 문제가 없지만,
장 마감 후 같은 날 재실행하면 이 행만 네이버 국내 행보다 하루 이전 기준일이 된다.
검수 화면이 행마다 기준일을 함께 보여주므로(§3.2 주의 2와 같은 이유) 담당자가 구분할 수 있다.

**폐기된 결론 — 기록으로 남긴다.** 아래 세 경로가 전부 막힌 것은 사실이다.

| 경로 | 결과 |
|---|---|
| 네이버 지수 API | `KOSPI`·`KPI200`은 되지만 **섹터지수 코드가 없다**. 추정 코드 4종 모두 실패 |
| KRX 정보데이터시스템(웹) 직접 호출 | 세션 쿠키를 실어도 `LOGOUT` 응답. 프로그램 접근 차단 |
| 공공데이터포털 금융위 주식시세정보 | **지수 오퍼레이션 자체가 없다.** 갱신도 기준일 +1영업일 13시 이후라 08:00 브리프에는 못 쓴다 |

여기서 "자동 소스 없음"으로 단정한 것이 잘못이었다. 막힌 것은 **KRX 웹사이트의 내부
엔드포인트**였지 KRX 가 별도로 제공하는 **Open API** 가 아니다. 셋을 확인하고 넷째를
찾지 않았다 — §3.5 의 "표본 2개로 규칙을 단정하지 말 것"과 같은 종류의 실수다.

### 3.4 시가총액 산출

해외사 시총 API는 대부분 유료 구간이므로 의존을 제거한다.

    시가총액(조원) = 종가 × 발행주식수 × (통화→KRW 환율) ÷ 1조

발행주식수는 분기 단위로만 바뀌므로 `Instrument.sharesOutstanding` 상수로 보관하고
분기 1회 갱신한다.

**국내사는 시드에 주식 수를 두지 않는다.** 네이버가 시총을 직접 주기 때문인데, 그 값은
현재가 기준이라 그대로 쓰면 실행 시각에 따라 흔들린다. 그래서 **응답에서 주식 수를
역산해 우리가 고른 거래일 종가로 다시 곱한다** — 방법과 한계는 §3.0 에 있다.

### 3.5 연초대비(YTD)

어떤 소스도 직접 제공하지 않으므로 별도 조회해 계산한다. 연중 변하지 않으므로
`YtdBasePrice` 테이블에 종목별 1행으로 캐시한다.

**기준가는 전년도 마지막 거래일의 종가다.** 국내 10종목 전부를 샘플 엑셀과 대조해 확정했다.

    연초대비 = (종가 - 전년 마지막 거래일 종가) / 전년 마지막 거래일 종가

이는 YTD의 표준 정의이기도 하다.

| 종목 | 샘플 역산 기준가 | 2025-12-30 종가 | 오차 |
|---|---|---|---|
| SK바이오사이언스 | 48,203 | 48,200 | 0.01% |
| 삼성바이오로직스 | 1,695,006 | 1,695,000 | 0.00% |
| 셀트리온 | 172,379 | 172,523 | 0.08% |
| SK바이오팜 | 124,594 | 124,600 | 0.00% |
| 한미약품 | 452,003 | 452,000 | 0.00% |
| 녹십자 | 159,008 | 159,000 | 0.00% |
| 알테오젠 | 345,784 | 345,868 | 0.02% |
| 리가켐바이오 | 173,693 | 173,700 | 0.00% |
| 에이비엘바이오 | 200,000 | 200,000 | 0.00% |
| 유바이오로직스 | 11,359 | 11,360 | 0.01% |

**폐기된 가설 — 기록으로 남긴다.** 초기에 SK바이오사이언스와 삼성바이오로직스 두 종목만
대조해 "당해 첫 거래일의 시가"로 단정했으나 틀렸다. 두 종목은 1/2 시가가 12/30 종가와
우연히 같았을 뿐이다(전일 종가 부근에서 시가가 형성되는 것은 흔하다).
그때 어긋난 셀트리온·한미약품을 "네이버 수정주가 탓"으로 오진했으나,
올바른 기준가를 쓰면 셀트리온 오차가 4.40%에서 0.08%로 떨어진다.
**수정주가는 문제가 아니었다.** 표본 2개로 규칙을 단정하지 말 것.

소스: 국내는 `api.finance.naver.com/siseJson.naver`의 전년 12월 마지막 거래일 종가,
미국은 Twelve Data `time_series`, 비미국 4종목은 **매일 도는 시세 소스와 무관하게 전부**
marketstack `/eod`(§3.2). 모두 전년 12월 하순 창을 조회해 마지막 거래일의 종가를 취한다.
연 1회 호출 후 캐시하므로 한도에 영향이 없다 — 이관 후 marketstack 소비가 연 3~4회로
떨어진 것이 이 캐시 덕분이다.

## 4. 아키텍처

이관(Supabase→MariaDB, Vercel→사내 AWS)과 소스 교체가 예정돼 있으므로,
변할 것으로 아는 부분을 전부 인터페이스 뒤에 둔다.

    src/
      domain/          순수 함수. 등락률·YTD·조원환산·표시 포맷. DB/네트워크 무관
      providers/
        quote/         QuoteProvider  ─ naver.ts, twelvedata.ts, marketstack.ts, krx.ts,
                                        lse.ts, six.ts
        news/          NewsProvider   ─ naver.ts
        summarize/     Summarizer     ─ gemini.ts  (후일 ollama.ts)
        fx/            FxProvider     ─ frankfurter.ts
      pipeline/        수집 → 클러스터링 → 요약 → 저장 오케스트레이션
      db/              Prisma 클라이언트 + 리포지토리
      auth/            secret.ts(상수 시간 시크릿 비교) + basic.ts(Basic 인증 판정)
      proxy.ts         Basic 인증 문지기(Next 16 미들웨어). 판정은 auth/ 에 있다
      app/
        api/cron/collect/route.ts   보호된 수집 트리거
        (review)/                   검수 UI

각 Provider는 도메인 타입만 반환한다. 소스가 바뀌어도 `providers/` 하위 파일
하나만 교체되고 `pipeline/`·`domain/`·UI는 손대지 않는다.

### 4.1 이관 3원칙

1. **Supabase를 그냥 Postgres로만 쓴다.** RLS·Realtime·Storage·Auth SDK 미사용.
   MariaDB 이관 시 `DATABASE_URL`과 Prisma `provider`만 바꾼다.
2. **Prisma 스키마를 Postgres/MySQL 공통 타입으로만 작성한다.**
   ID는 앱에서 `cuid()` 생성(DB 시퀀스·UUID 확장 미사용), enum 대신 문자열 + 앱 레벨 검증,
   금액·비율은 `Decimal`, 시각은 `DateTime` UTC 저장.
3. **스케줄러를 코드에 넣지 않는다.** 수집은 `POST /api/cron/collect`(공유 시크릿 헤더)로만
   기동한다. 초기엔 Vercel Cron이, 사내에선 crontab의 `curl` 한 줄이 같은 엔드포인트를 부른다.

## 5. 데이터 모델

    Instrument          고정 종목 마스터
      id, category(국내사|해외사|Index), displayOrder, name,
      currency, sharesOutstanding?, quoteSource, quoteSymbol, newsQuery

    YtdBasePrice        연초 기준가 캐시(전년 마지막 거래일 종가)
      instrumentId, year, price                      (unique: instrumentId+year)

    BriefRun            일자별 수집 실행
      id, tradeDate, status(COLLECTING|READY|FAILED), startedAt, finishedAt

    QuoteSnapshot       종목별 시세
      runId, instrumentId, price, prevDiff, changePct, ytdPct,
      marketCapKrwTrillion?, fxRate?, sourceName, fetchedAt

    NewsCandidate       뉴스 후보 (종목당 최대 3)
      runId, instrumentId, rank(1..3), title, url, publisher,
      publishedAt, clusterSize

    NewsSummary         요약 후보 (후보당 3)
      candidateId, variant(1..2), text            (text 길이 ≤ 100, 공백 포함)
                                                  (2026-08-28 이전 실행에는 variant=3 행이 남아 있다)

    Selection           담당자 선택
      runId, instrumentId, decision, chosenCandidateId?, chosenSummaryId?,
      editedText?, updatedAt                       (unique: runId+instrumentId)

    decision 값
      PENDING    아직 검토하지 않음 (기본값)
      SELECTED   뉴스 1건 + 요약 1안 선택 완료
      OMITTED    후보가 있지만 담당자가 싣지 않기로 결정

`OMITTED`는 시스템이 후보를 못 만든 경우(후보 0건)와 **의미가 다르다.**
전자는 담당자의 판단, 후자는 데이터 부재다. 출력은 둘 다 공란이지만
검수 화면에서는 구분해 표시하고, 미검토(`PENDING`) 행이 남아 있으면
2단계의 최종 확정을 막는 근거로 쓴다.

`Selection`을 분리해 두면 재수집이 담당자 선택을 덮어쓰지 않는다.

## 6. 파이프라인

`POST /api/cron/collect` 실행 순서:

1. **BriefRun 생성** — 두 날짜 기준을 구분한다.
   `tradeDate` = 시세 기준일 = **직전 영업일**(종가 출처).
   뉴스 검색 범위 = **실행 당일과 그 전날**(§7). 둘은 일치하지 않을 수 있다
   (예: 월요일 실행 시 시세는 금요일 종가, 뉴스는 일·월요일 기사).
2. **환율 수집** — Frankfurter 1회 호출, USD/EUR/GBP/CHF/HKD → KRW
3. **시세 수집** — 종목별 Provider 호출. 실패한 종목은 해당 행만 비우고 계속 진행
4. **YTD 보정** — `YtdBasePrice` 미보유 종목만 전년 마지막 거래일 종가 조회 후 캐시
5. **뉴스 수집** — 종목별 네이버 검색 API. 당일·D-1 기사만 필터
6. **클러스터링** — 상위 3개 선정 (§7)
7. **요약 생성** — 후보당 2안 (§8)
8. **status = READY**

한 종목의 실패가 전체를 막지 않는다. 각 단계는 개별 종목 단위로 격리된다.

## 7. 뉴스 "빈도 상위 3개" 산출

네이버 검색 API는 정렬이 `sim`/`date`뿐이라 빈도를 직접 계산해야 한다.

1. `Instrument.newsQuery`로 검색 (`sort=date`, `display=100`)
2. `pubDate`가 당일 또는 D-1인 기사만 남긴다
3. 제목 정규화: 언론사명·대괄호 말머리·기호 제거, 공백 정리
4. 정규화 제목의 토큰 자카드 유사도로 클러스터링 (임계값 0.5)
5. **클러스터 크기 = 몇 개 매체가 다뤘는가 = 보도 빈도**. 상위 3개 클러스터 선정
6. 각 클러스터에서 대표 기사 1건 선정 (네이버뉴스 링크 보유 > 최신순)

**관련성 필터 (실측으로 추가 확정).** 클러스터링 전에 제목에 종목 별칭이 포함된 기사만 남긴다.
필터 없이 실행한 결과 삼성바이오로직스·알테오젠의 상위 3개가 전부 코스피 시황 기사였다
(통신사 배포 기사가 수십 매체에 동시 게재되어 개별 기업 뉴스를 빈도로 압도한다).
필터 적용 후 6개 종목 전부 관련 기사만 상위에 남았다. 지수 행은 별칭이 "코스피"이므로
같은 규칙으로 시황 기사가 정확히 통과한다.

**한계 — 하루에 큰 뉴스가 하나뿐이면 후보 3개가 같은 사건이 된다.**
실측: 셀트리온 상위 3개가 모두 "램시마SC·짐펜트라 상반기 4562억" 변형이었다.
클러스터 비교를 전 멤버 대상으로 바꿔 흩어진 조각을 흡수했으나(21→35개 매체),
임계값을 0.5에서 0.3까지 낮춰도 서로 다른 3개 사건이 나오지 않는다.
한국어 헤드라인은 같은 사건도 표현 차이가 커서 자카드 유사도로 사건 경계를 가를 수 없다.
그날 존재하지 않는 선택지를 만들어낼 수는 없으므로 이 동작을 그대로 둔다.
**결정 (사용자 확정)**: 후보 3개를 모두 표시하되, 상위 후보와 같은 사건으로 판정되면
"같은 사건" 표시를 붙인다. 담당자가 선택지가 실질적으로 하나임을 화면에서 바로 알 수 있고,
표현이 다른 제목 중에서 고를 여지는 남는다.

구현: 후보 3건을 확정한 뒤 대표 기사 제목끼리 자카드 유사도를 계산해,
자기보다 상위 순위 후보와 임계값 이상이면 `sameEventAsRank`에 그 순위를 기록한다.
클러스터링 임계값(0.5)보다 낮은 값을 쓴다 — 클러스터로 묶이지 않았다는 것은
이미 0.5 미만이라는 뜻이므로, 표시용 판정은 0.3 안팎을 쓴다.
검수 UI는 이 값이 있는 후보에 "1위와 같은 사건" 같은 배지를 단다.

Index 행도 개별 종목과 동일하게 처리한다. 샘플에서 Nasdaq 칸이 비어 있는 것은
지수를 제외해서가 아니라 그날 쓸 만한 기사가 없었기 때문이다.

**감점 순위 (실측으로 추가 확정).** 클러스터 크기 하나로만 정렬하면 두 가지가 깨진다.
(1) 큰 뉴스가 없는 날은 모든 후보가 1개 매체라 순위가 사실상 무작위다.
(2) 홍보성 보도자료가 여러 매체에 동시 배포되면 진짜 뉴스를 밀어낸다 — 실측(2026-08-27)에서
알테오젠 1순위가 3개 매체가 받은 「생물공학 상장기업 브랜드평판 8월 빅데이터 분석결과…1위
알테오젠」이었고, 1개 매체뿐인 「K-바이오 1~8월 기술수출 17조…알테오젠 'ALT-B4' 1100억 돌파」가
3순위로 밀려 있었다. 그래서 제목만 보고 감점을 매기고 **감점 오름차순 → 클러스터 크기 내림차순**
으로 정렬한다. 감점 대상은 자동생성 주가 기사(가장 큰 감점), IR 뉴스가 아닌 장르(브랜드평판
집계·광고 회고 칼럼·수급표·종목추천·사진 기사), 증시 시황 종합(가장 작은 감점) 세 단계다.

**감점이지 필터가 아니다.** 후보를 제거하지 않고 뒤로만 민다. 하드 필터로 하면 패턴이 과하게
걸려 후보가 0건이 된 행을 화면이 「당일·D-1 기사 없음」이라고 **단정**한다 — 기사가 있었는데도.
그것은 이 프로젝트가 반복해서 고쳐 온 실패 모드(실패·누락을 정상적인 공란으로 렌더하는 것)와
같은 것이다. 감점은 그 경로를 만들지 않는다: 후보 수는 규칙과 무관하게 늘 그대로이고, 규칙이
틀렸을 때의 최악은 "순서가 나쁘다"이지 "없다고 거짓말한다"가 아니다.

**시황·수급은 그것을 원하는 행에서는 감점 대상이 아니다.** KOSPI·S&P500·Nasdaq 행이 원하는
것이 바로 그 기사다. 감점 함수는 `wantsMarketWrap` 을 받아 이 두 규칙만 해당 행에서 건너뛴다.
자동생성 주가 기사는 그 행에서도 감점한다(지수의 자동생성 기사에도 값이 없다).

**예외의 기준은 `isIndex` 가 아니다.** 처음에는 둘이 같아 보였다 — 지수 행이 셋뿐이었고 셋 다
시황을 원했기 때문이다. 코스피200 헬스케어 행에 업종 검색어를 준 뒤로 그 전제가 깨졌다:
이 행도 지수지만 원하는 것은 시황이 아니라 업종 동향이다. 실측(2026-08-27)에서 `isIndex` 로
가르면 미국 증시 시황 두 건이 감점 없이 업종 기사와 동률이 되어, 정작 업종 기사인
「한미약품 3.5조 잭팟에 제약株 불붙었다」가 2순위로 밀렸다. 그래서 어느 행이 시황을 원하는지를
`src/pipeline/collectHelpers.ts` 의 `MARKET_WRAP_ROWS` 에 **이름으로 명시**한다. 검색어 문자열로
추론하지 않는다 — 검색어를 바꾸는 순간 감점 규칙이 조용히 따라 바뀌기 때문이다.

패턴과 무게는 `src/pipeline/cluster.ts` 의 `PENALTY_RULES` 한곳에 모여 있고,
**담당자 인터뷰 후 조정 가능**하다.

**코스피200 헬스케어 행만 검색어가 업종 단위다.** 나머지 22행은 그 종목·지수 자신의 이름으로
찾지만 이 행은 `제약주` 로 찾고 별칭은 `제약` 이다. 이유는 두 가지다. 첫째, `코스피200 헬스케어`
는 실측 0건이다(2026-08-27) — 그 표현을 제목에 쓰는 언론이 없어 이 행의 뉴스 칸이 매일 비었다.
둘째, 원본 샘플 엑셀의 이 칸에 실제로 들어 있던 기사가 지수 자체의 뉴스가 아니라 업종 전체에
영향을 주는 뉴스였다: 「美 FDA, 의약품 용기 지침 바뀐다…삼성·셀트리온 시밀러도 영향」. IR 팀은
이 칸을 "헬스케어 업종 동향"으로 쓰고 있었다 — KOSPI 행에 시황이 들어가는 것과 같은 성격이다.
검색어 후보를 같은 조건에서 비교한 결과(2026-08-27) `제약주` 가 샘플에 가장 가까웠고
(「한미약품 3.5조 잭팟에 제약株 불붙었다」), `제약바이오` 는 개별 기업 뉴스로, `헬스케어` 는
제약·바이오와 무관한 기사(「세라젬 BCI」「풀무원헬스케어」)로 채워졌다. 별칭을 `제약` 으로 둔
것은 한자 표기 `제약株` 까지 함께 잡기 위해서다. **잠정 결정이며 담당자 인터뷰 후 조정 가능하다.**

당일·D-1 기사가 하나도 없으면 후보를 만들지 않는다 → 해당 칸은 공란으로 출력된다.

## 8. 요약 생성

- 대표 기사의 **본문을 크롤링**해 입력으로 쓴다 (`n.news.naver.com` 링크 우선).
  크롤링 실패 시 검색 API의 `description` 스니펫으로 자동 폴백한다.
- 기사 1건당 요약 **2안**을 한 번의 호출로 생성한다 (2026-08-28 에 3안에서 줄였다, §8.3).
- **각 요약은 공백 포함 100자 이내.** `[...text].length <= 100`으로 검증한다
  (한글·이모지 안전을 위해 `String.length` 대신 코드포인트 배열 길이 사용).
  초과 시 문장 경계에서 절삭한다(`domain/text.ts` 의 `truncateAtSentence`).

  **재생성은 하지 않는다 (2026-08-27 확정, 최초안의 "1회 재생성"을 철회).**
  초안은 "초과 시 1회 재생성, 그래도 초과하면 절삭"이었으나 세 가지 이유로 뺀다:

  1. **같은 프롬프트로 다시 물어도 짧아질 이유가 없다.** 100자를 넘기는 것은
     그 모델의 계통적 성향이지 우연이 아니다(`gemini-3.1-flash-lite` 실측).
     실제로 효과를 보려면 "직전 답이 N자였으니 줄여라"는 교정 프롬프트가 필요한데,
     그건 "1회 재생성"이 뜻하는 것과 다른 변경이다.
  2. **무료 티어의 일일 쿼터가 이 시스템의 실질 제약이다.** 모델별로 소진되며
     (§8.1, `MODEL_CHAIN`·`exhaustedModels`), 소진되면 그 뒤 **모든** 요약이
     더 약한 모델로 내려간다. 요약 한 건의 절삭을 고치려고 그날 남은 전부의
     품질을 거는 교환이 된다.
  3. **호출 지연 8초 × 최대 69회**(§8.1.7)라 07:40~08:00 창에서 재호출 비용이
     작지 않다.

  대신 절삭이 품질을 실제로 해치지 않도록 두 가지를 둔다: 절삭 결과가 예산의
  절반에도 못 미치면 문장 경계를 버리고 100자에서 하드 컷하며(`truncateAtSentence`),
  검수 화면은 선택한 요약을 담당자가 직접 고칠 수 있게 한다(§9).
### 8.1 실측에서 확인된 구현 제약

1. **모델은 하나로 고정하지 않는다 — 순서 있는 폴백 체인을 둔다.**
   (2026-08-27 확정. 초안의 "`gemini-3.6-flash`로 고정한다"를 철회했다.)

   무료 티어의 일일 요청 한도는 **모델별로** 따로 소진된다(실측: `gemini-3.6-flash`가
   429 `GenerateRequestsPerDayPerProjectPerModel-FreeTier`를 반환하는 순간에도
   `gemini-3.5-flash-lite`는 200을 돌려줬다). 따라서 모델을 늘리면 하루에 쓸 수 있는
   총량이 늘어난다. 체인은 `MODEL_CHAIN_ENTRIES`(`src/providers/summarize/gemini.ts`)에
   있고, 2026-08-28 기준 **7개**이며 **전원 `verified`** 다(같은 날 5개→8개로 넓혔다가,
   실측 재검증에서 `gemma-4-31b-it`를 빼 7개가 됐다. Task 33).

   - **순서가 곧 품질 정책이다.** 검증된 모델을 앞에, 품질을 아직 신뢰할 수 없는
     모델을 뒤에 둔다. 요약은 품질이 나빠도 화면에서 "요약처럼" 보이므로, 좋은
     모델을 앞에 두는 것 자체가 안전장치다 — 평상시 담당자에게 가는 것은 검증된
     결과이고, 뒤쪽 모델은 앞이 전부 소진된 날에만 "빈칸보다는 낫다"의 자리에서 일한다.
     그래서 체인은 이름 문자열 배열이 아니라 `{ model, quality, note }` 구조체다.
     `quality`(`verified` | `last-resort`)의 순서 불변식은 테스트가 지킨다.
     **현재 `last-resort` 인 모델은 없다.** 그 등급이 비었다고 해서 지우지는 않는다 —
     다음에 "빈칸보다는 낫다" 후보가 생기면 그 자리를 명시할 수단이 필요하다.
     대신 테스트가 두 갈래로 지킨다: 순서 불변식은 `last-resort` 가 하나라도 있을 때만
     적용되고(조건부), 여기에 **"체인이 전원 `verified` 인가"** 를 별도 단언으로 세웠다.
     검증 안 된 모델을 끼워 넣으려면 그 테스트를 **의식적으로** 고쳐야 한다.
   - **한 줄 요약: 체인을 넓히면 발췌 폴백이 줄어들지만 없어지지는 않는다.**
     2026-08-28 실측에서 5개 체인이 후보 47건 중 32건을 덮었다. 7개면 47건을 덮을
     가능성이 높지만, **모델별 한도는 공개돼 있지 않고 날마다 다르다.** 발췌 폴백
     경로(`buildFallbackSummaries`)와 화면의 「본문 발췌」 배지는 그대로 유지한다.
   - **어느 모델이 답했는지는 `NewsCandidate.summaryModel`에 남는다.** 체인이
     길어질수록 이 값이 중요해진다 — 요약 품질이 이상한 날에는 이 컬럼부터 본다.
   - **체인에 넣지 않기로 한 모델은 사유와 함께 `EXCLUDED_MODELS`에 남긴다.**
     `gemini-2.5-*`는 신규 키에 404(영구 실패)라 체인을 넘기는 조건에 해당하지 않아
     그 뒤 모델을 무력화한다. `gemini-3.7-flash`·`gemini-flash-latest`는 실측할
     때마다 503이라 품질을 측정하지 못했다 — 추측으로 순서를 매기지 않는다.
     gemma 계열 **둘 다** 뺐다 — `gemma-4-26b-a4b-it`는 JSON은 내지만 내용이 무너지고
     (아래 2번), `gemma-4-31b-it`는 타임아웃이 수집 창을 갉아먹는다(아래 3번).
2. **JSON은 냈는데 내용이 무너지는 모델이 있다 — 체인 후보의 판정 기준은
   "JSON이 파싱되는가"가 아니다.** `gemma-4-26b-a4b-it` 실측(2026-08-28, 10회):
   5회는 120초를 넘겼고(프로덕션 타임아웃 60초), 4회는 `finishReason=STOP`인 정상
   응답 안에서 프롬프트 자리표시자를 본문에 흘리거나("1안(수치 중심): …"), 한국어가
   깨지거나("체결질적적 변화", "가동률 회솔복"), `<em>undercut</em>`을 110회 반복한
   2,081자를 냈다. 이 출력은 100자로 절삭되어 **정상 요약과 똑같이 「① 수치 중심」
   라벨을 달고** 화면에 오른다. 발췌 폴백은 최소한 「본문 발췌」 배지가 붙고 본문에서
   그대로 오려낸 문장이므로, 이 모델은 "빈칸보다는 낫다"가 아니라 **발췌보다도 나쁘다.**
   그래서 체인에 넣지 않았다.
3. **느린 모델은 그 자체로 비용이다 — `gemma-4-31b-it`를 뺀 이유(2026-08-28).**
   한동안 체인 8순위에 있었다. 짧은 합성 기사로 잰 첫 표본(26회 중 20회 성공)이
   대표적이지 않았고, **실제 크롤링 본문** 24회로 재니 **타임아웃 12 / 코드펜스 12 /
   펜스 없는 정상 JSON 0** 이었다.

   **결정적 근거는 타임아웃 비용이다.** 한 번이 60초이고 요약 동시성은 4다. 이 모델까지
   내려간 날 후보 20건이 닿으면 20 × 60초 ÷ 4 = **5분**을 순수 대기로 쓴다 — 시세·뉴스·
   요약을 모두 처리해야 하는 07:40~08:00 창(20분)의 **4분의 1**이다. 수율 50%짜리
   모델에 그만큼을 걸 수 없다. **체인 후보의 판정 기준에는 응답 시간도 들어간다.**

   조용한 실패도 겹쳤다: 파싱된 12건 중 1건은 내용이 무너져 있었다(`유럽으로의 시장으로의
   확장 … same-day same-day own ow`). 위 2번과 성질이 같고 비율만 40% → 8%로 낮다.
   발췌 폴백은 배지가 붙고 본문에서 그대로 오려낸 문장이라 이미 정직하므로, 이 모델을
   두고 얻는 것("8순위까지 내려간 날에만, 절반의 확률로, 발췌 대신 요약")이 비용보다 작다.
4. **체인을 넘기는 조건은 세 가지, 던지는 조건은 하나다.**
   - `429`/`RESOURCE_EXHAUSTED` → 그 모델의 하루치 소진. **기록**하고 다음 모델
     (기록은 KST 일 경계에 리셋된다).
   - `503`/`500`/`UNAVAILABLE` → 구글 쪽 일시적 장애. 기록하지 않고 다음 모델.
   - **응답을 아예 못 받은 경우**(타임아웃 60초·네트워크 오류) → 기능적으로 503과
     같다. 기록하지 않고 다음 모델. 2026-08-28 이전에는 이 경로가 없어서 `fetch`가
     던지면 **체인 전체가 거기서 끝났다** — 3번 모델의 타임아웃 한 번에 남은 5개를
     시도조차 못 하고 그 후보가 발췌 폴백으로 떨어졌다. 체인이 길어지면서
     손실이 커져 고쳤다. 판정 기준은 시세 경로(`quote/retry.ts`)와 한 벌을 공유한다
     (`providers/transientNetwork.ts`) — 목록이 갈라지면 "시세는 재시도하는데 요약은
     안 하는" 상태가 조용히 생긴다.
   - 그 밖(세이프티 차단·인증 오류·JSON 파싱 실패)은 **던진다.** 다른 모델로 넘기면
     진단 가능한 에러가 가려진다.

   전부 실패했을 때의 사유 문구는 이 세 범주를 **갈라서** 적는다. 운영자가 볼 곳이
   서로 다르기 때문이다 — 쿼터는 기다리는 문제, 503은 구글 쪽 문제, 응답 없음은
   우리 쪽 네트워크·타임아웃 문제다.
5. **JSON 파싱 실패 시 코드펜스를 한 번만 의심한다.** 정상 `JSON.parse`를 먼저
   시도하고, **실패했을 때만** ```` ```…``` ```` 를 벗겨 재시도한다. 규약을 지키는
   모델(체인의 gemini 7개는 실측상 한 번도 펜스를 붙이지 않았다)은 이 경로를
   지나가지 않으므로 평상시 동작이 바뀌지 않는다. 벗겨낸 뒤에도 실패하면 그대로
   실패다 — 깨진 응답을 억지로 살리면 그게 정상 요약처럼 화면에 오른다.

   **복구했으면 경고 로그를 남긴다.** 조용히 고쳐주면 그 모델이 계속 규약을 어겨도
   아무도 모른다. 실측(2026-08-28, 당시 체인에 있던 `gemma-4-31b-it`): `responseMimeType`이
   `application/json`인데도 **여는 펜스 없이 닫는 펜스만** 붙어 왔다(표본 3개 모두) —
   여닫이가 맞는 펜스만 벗기도록 만들었으면 실제 실패를 하나도 못 잡았을 것이다.

   **그 모델을 뺀 지금(3번) 이 경로를 쓰는 모델은 없다. 그래도 지우지 마라 — 죽은
   코드가 아니다.** 정상 파싱이 실패했을 때만 도는 경로라 비용이 0이고, 경고 로그가
   **감지 장치** 역할을 한다: 이 로그가 뜬다면 규약을 어기는 모델이 새로 생겼다는
   뜻이고, 그때 그 모델의 품질을 다시 재면 된다. 남은 gemini 7개는 실측상 펜스를
   붙인 적이 한 번도 없다.
6. **응답 파싱 시 `parts[0].text`를 그대로 쓰면 안 된다.** Gemini 3.x는 파트에
   `thoughtSignature`를 함께 실어 보낸다. `thought`가 아닌 text 파트를 골라야 한다.
7. **호출 지연이 1건당 약 8초다.** 사고 토큰이 출력의 7배 이상 발생한다
   (실측: 출력 197 / 사고 1,503). 종목 23 × 후보 3 = 최대 69회이므로 순차 실행 시
   9분 이상 걸린다. 07:40~08:00의 20분 안에 끝내려면 **동시성 제한을 건 병렬 호출**이
   필수다. 무료 티어 RPM 한도에 맞춰 동시 실행 수를 설정값으로 뺀다.
   체인 뒤쪽 모델은 이보다 느릴 수 있다 — `gemini-3-flash-preview`는 사고 토큰이
   8,300여 개라 실측 34초다(60초 타임아웃 안이지만 여유가 크지 않다). 앞쪽 모델이
   모두 소진돼 이 모델까지 내려온 날은 수집 전체가 느려진다.

### 8.2 사전 생성 대 온디맨드

요약을 담당자가 뉴스를 고른 뒤 생성하면 호출이 69회에서 23회로 준다.
그러나 담당자가 매번 8초를 기다리게 된다. **아침 시간 단축이 이 시스템의 목적**이므로
사전 생성을 택한다. 담당자 대기는 0이다.

- 2안은 서로 달라야 한다: **① 수치 중심 ② 배경·맥락 중심**.
  (확정. 담당자 인터뷰 후 조정 가능하도록 프롬프트를 상수로 분리해 둔다.)

### 8.3 ③ 시사점 중심을 뺀 이유 (2026-08-28)

초안은 3안이었고 세 번째가 **③ 시사점 중심**(회사·시장에 주는 함의)이었다. 뺐다.

근거는 원본 샘플 엑셀이다. **실제로 나가는 요약문은 전부 사실·수치 중심이고
해석이 없다:**

> IDT 바이오로지카 인수 통한 글로벌 공급망 사업자 영역 확장 전략…지난해 연결 매출
> 6,513억원 달성, 전년 대비 두 배 넘는 성장

> 헌터라제 IV 인도·대만 허가로 해외 14개국 허가국 확대…ICV 대만·페루 등 4개국 허가,
> 국내 2027년 허가 목표

반면 모델이 만든 3안은 이런 문장이었다 — **"기업 가치 재평가의 핵심 모멘텀이 될
것으로 기대됨"**. **전 임원에게 나가는 문서에서 모델이 지어낸 전망이 가장 위험하다.**
담당자가 걸러낼 수는 있지만, 애초에 만들지 않는 편이 낫다.

**이 결정은 한도 문제와 무관하다.** 호출 수는 그대로다 — 2안이든 3안이든 후보
1건당 1회 호출이고, Gemini 무료 한도는 **요청 수** 기준이다. 줄어드는 것은 출력
토큰뿐이다. §8.1 의 체인 확장과 묶어서 읽지 마라.

**되돌리기는 쉽다.** 관점 정의(`SUMMARY_VARIANTS`)와 프롬프트가 `prompt.ts` 에
상수로 모여 있다. 되돌린다면 함께 바뀌어야 하는 곳은 `gemini.ts` 의
`responseSchema`·`SummarySet` 둘뿐이다. 화면 라벨과 발췌 폴백 개수는
`SUMMARY_VARIANTS` 에서 파생되므로 자동으로 따라온다.

**이미 저장된 `variant = 3` 행은 남아 있다.** 재수집하면 사라지지만 그 전에 화면을
열면 그대로 보인다. 화면은 `SUMMARY_VARIANTS` 에 없는 variant 를 만나도 깨지지 않고
「3안 (지금은 만들지 않는 관점)」으로 표시한다 — 「③ 시사점 중심」으로 되살려 적지는
않는다. 그렇게 적으면 빼기로 한 관점이 화면에서 정상 선택지로 복원되기 때문이다.

## 9. 검수 UI

`/review/[date]` 단일 화면.

**인증은 환경변수로 켜고 끄는 최소 Basic 인증 하나뿐이다** (2026-08-31 개정).
원래 "인증 없음(1단계 결정)"이었고 그 전제는 **사내망 배포**였다. 임시로 공개
URL(Render)에 올리게 되면서 전제가 깨졌다 — 공개 주소에서는 누구나 검수 화면의
서버 액션으로 담당자의 선택을 바꿀 수 있고 엑셀도 그냥 받아진다.

그래서 `src/proxy.ts` 가 `BASIC_AUTH_USER`/`BASIC_AUTH_PASSWORD` 로 문지기를 선다.
판정은 `src/auth/basic.ts` 한 곳에 있다.

- **둘 다 없으면 인증이 꺼진다.** 로컬 개발과 사내망 배포는 예전 그대로 돈다.
- 둘 다 있으면 대조하고, 틀리면 401 이다.
- **한쪽만 있으면 모든 요청을 401 로 막는다.** 통과시키면 "인증이 걸린 줄 아는
  무방비 상태"가 되는데 그건 화면상 정상과 구분되지 않는다. 열어두는 대신 닫고
  이유를 로그에 남긴다.
- `/api/cron/collect` 는 matcher 에서 **제외**한다. 크론은 `CRON_SECRET` 으로 스스로
  인증하며, Basic 인증까지 얹으면 §4.1-3 의 "crontab 의 `curl` 한 줄"이 깨진다.
- 시크릿 대조는 `src/auth/secret.ts` 의 상수 시간 비교 하나를 크론 라우트와 함께
  쓴다. **같은 보안 판정을 두 벌 두지 않는다.**

로그인 화면·세션·사용자 테이블은 없다. 사람마다 다른 계정도, 감사 로그도 없다.
2단계에서 사내 인증으로 통째로 교체될 자리라 더 짓지 않았다(§12).
임시 배포 절차는 `docs/render-배포.md` 에 있다.

### 9.1 셸 — 왼쪽 사이드바 / 오른쪽 내용

시스템 이름은 **IR Daily Brief**.

    ┌────────────┬──────────────────────────────────┐
    │ 사이드바    │  헤더(제목 + Excel 다운로드)       │
    │ 고정 280px  │  ─────────────────────────────── │
    │ sticky      │  실행 상태 배너 / 23행 브리프 표   │
    └────────────┴──────────────────────────────────┘

사이드바에 담기는 것은 **날짜 네비게이션뿐이다.** 브랜드 블록, 보고 있는 날짜,
「◀ 이전 / 다음 ▶」, 월 달력, 「최근 브리프」 목록.

**메뉴 항목을 지어내지 않는다.** 이 시스템에는 아직 브리프 화면 하나뿐이고,
눌러도 아무 일이 일어나지 않는 메뉴는 빈 사이드바보다 나쁘다. 날짜 네비게이션이
곧 메뉴다. 필터·등록 버튼 같은 것도 두지 않는다.

「◀ 이전 / 다음 ▶」은 **하루씩 움직이지 않는다.** 수집이 평일에만 돌기 때문에
하루씩 넘기면 주말마다 「브리프 없음」에 떨어진다. 실제로 데이터가 있는 이웃
날짜로 건너뛰고(`adjacentBriefDates`), 없으면 링크가 아니라 흐린 글자다.

**셸은 `layout.tsx` 가 아니라 페이지가 감싼다.** 달력의 월 이동이 `?m=YYYY-MM`
쿼리에 상태를 두는데 App Router 의 layout 은 `searchParams` 를 받지 않는다.
셸을 페이지에서 감싸면 달력이 링크만으로 동작하고 클라이언트 자바스크립트가 0 이다.

### 9.2 톤앤매너

따뜻한 뉴트럴. 팔레트는 **`src/app/globals.css` 의 `@theme` 토큰 한 곳에만** 있다
(사이드바 `#3B352E`, 본문 `#FFFFFF`, 표 헤더 `#FAF8F5`, 행 구분선 `#EFEBE4`,
기본 버튼 `#2E2A24`, 강조 `#C0392B`). 한국어 본문 폰트는 `Noto Sans KR`.

토큰 이름은 색이 아니라 **뜻**으로 짓는다(`--color-fail`, `--color-pending`).
이 화면의 안전장치가 색 구분 하나에 걸려 있어서, 색이 컴포넌트마다 흩어지면
다음에 톤을 바꿀 때 한 군데를 빠뜨리는 순간 두 상태가 같은 색으로 수렴한다.

**숫자 열에는 상승/하락 색을 쓰지 않는다.** 한국 시장 관행에서 빨강은 상승이라
음수에 빨강을 칠하면 훑어보는 담당자를 정반대로 오독하게 만든다. 방향은 `▲`/`▼`
기호가 말한다. `#C0392B` 는 오류·한도 초과 문구에만 쓴다.

### 9.3 표와 행 패널

- 23행 브리프 표. 선택이 반영된 최종 형태 그대로 보인다.
- 행 클릭 → 그 행 아래로 펼쳐지는 패널:
  - 뉴스 후보 3건 (제목·언론사·시각·보도빈도·원문 링크) → 라디오 선택
  - **네 번째 선택지: "이 행에 뉴스 싣지 않음"** → `decision = OMITTED`.
    후보가 있어도 담당자가 게재하지 않기로 결정할 수 있다.
  - 선택한 뉴스의 요약 2안 → 라디오 선택 + 직접 수정 가능
- 선택 즉시 `Selection`에 저장 (자동 저장, 별도 저장 버튼 없음)
- **행 상태는 여섯 가지이고 서로 구분되어 보여야 한다**(`RowState`).
  후보 0건이면서 검색 성공 → 「당일·D-1 기사 없음」(`-`) / 후보 0건이면서 검색 실패
  → 「뉴스 조회 실패 — 확인 필요」 / `OMITTED` → `-` + 「싣지 않음」 / `PENDING` →
  「미확정 · 1순위 후보」 미리보기 / `SELECTED` → 확정본 / `STALE_SELECTION` →
  「선택 무효화됨」. 이 밖에 「시세 실패」·「환율 미확보」·「본문 발췌」·「기준일 미상」·
  「(수기)」·「n 대체」 표시가 있다. **톤을 바꿀 때 이 구분이 무너지면 안 된다.**

### 9.4 달력

사이드바의 월 그리드. 기본은 보고 있는 날짜의 달이고, 월 이동은 `?m=YYYY-MM`
링크다(서버 렌더, 클라이언트 상태 없음).

- 브리프가 **있는 날짜만 링크**다. 없는 날짜는 흐린 글자에 커서도 기본이라
  누르기 전에 알 수 있다 — 눌러도 아무것도 없는 화면으로 가는 것보다 정직하다.
- 있는 날짜는 점 색으로 **완료 / 부분 완료 / 수집 중 / 실패**를 가른다
  (`briefDayMark`). **부분 완료를 완료와 합치지 않는다.** 모르는 상태 문자열은
  조용히 완료로 떨어뜨리지 않고 `UNKNOWN`(회색)이다.
- 그 달에 실제로 나타난 표시만 아래 범례에 적는다.
- 오늘은 테두리, 보고 있는 날짜는 채운 배경. 주말은 흐리다(수집이 평일만 돈다).
- 이웃 달 날짜는 회색으로 채우지 않고 빈 칸이다 — 조회하지 않은 달을
  「브리프 없음」인 것처럼 그리면 화면이 모르는 것을 아는 것처럼 말하게 된다.
- 데이터는 `listBriefDates(yearMonth)` — `runDate`·`status` 두 열만 읽는다.
  날짜 키는 URL 키인 **`runDate`** 다(`tradeDate` 가 아니다).

### 9.5 엑셀 출력

본문 헤더 우측 「Excel 다운로드」 → `GET /api/export/[date]`
(`force-dynamic`, `Content-Disposition: attachment`,
파일명 `IR_Daily_Brief_YYYY-MM-DD.xlsx`).

형식은 원본 브리프 엑셀과 같다 — 행1 공백, 행2 표 제목, 행3~4 머리글
(시가총액 아래 「(조원)」), 행5부터 종목당 2행(구분~시가총액은 세로 병합,
뉴스만 1행=제목 / 2행=요약문). `%`·연초대비는 **소수로 저장하고 셀 서식이
백분율**이다(문자열이면 엑셀에서 계산이 안 된다). 시가총액은 소수 둘째 자리.

데이터는 화면과 **같은 `getBriefRows`·같은 `newsColumnContent`** 를 쓴다.
엑셀용 조회를 따로 두면 화면과 파일이 다른 내용을 보여줄 수 있다.
표 → 셀 변환은 순수 함수(`src/domain/excel.ts`)가 하고 워크북 조립
(`src/export/workbook.ts`)은 받은 값을 적기만 한다.

**확정된 내용만 내보낸다.** 이 파일은 메일에 붙어 전 임원에게 나간다.

| 행 상태 | 뉴스 칸 |
|---|---|
| `SELECTED` | 고른 제목 / 고른(또는 수정한) 요약 |
| `PENDING` · `STALE_SELECTION` | **빈 칸** — 화면의 미확정 미리보기는 절대 내보내지 않는다 |
| `OMITTED` · 후보 없음 | `-` |
| 조회 실패 | **「뉴스 조회 실패 — 확인 필요」** |

**세 결과는 서로 다른 사실이라 합쳐지면 안 된다.** 빈 칸 = "아직 정해지지 않았다",
`-` = "실을 것이 없다고 **정해졌다**", 조회 실패 문구 = "확인하지 **못했다**".

조회 실패를 `-` 로 내보내지 않는 이유가 이 절에서 제일 중요하다. 이 파일에서 `-` 는
**사실 주장**이고, 메일을 받는 사람에게는 "오늘 이 회사 뉴스가 없었다"로 읽힌다.
실제로는 검색이 실패해 우리가 모르는 것이다 — 화면에서 「기사 없음」과 「조회 실패」를
갈라 놓은 것(§9.3, `NEWS_FAILED`)과 같은 이유이고, 그 구분이 파일에서 무너지면
화면에서 없앤 거짓말이 파일에서 되살아난다. 문구는 화면 라벨을 그대로 가져와
(`rowStateLabel('NEWS_FAILED')`) 두 곳이 어긋날 수 없게 한다.

`OMITTED` 와 후보 없음만 같은 `-` 로 둔다. 둘 다 "실을 것이 없다고 정해졌다"이고,
왜 없는지는 담당자의 관심사(화면에서 「싣지 않음」으로 갈린다)이지 메일 받는 사람의
판단에 쓰이지 않는다.

다운로드는 막지 않되 **누르기 전에** 화면이 몇 건이 비는지와, 조회 실패 몇 건이
그 문구를 달고 나가는지 알려준다. 빈 칸 수는 상태를 다시 세지 않고
`toExcelRows` 결과에서 센다 — 판정이 두 곳이면 경고가 파일과 어긋난다.

**엑셀 칸은 화면 칸보다 더 확정된 것처럼 보이면 안 된다.** 시세 조회 실패는
공란이 아니라 「시세 실패」, 환율 미확보는 「환율 미확보」, 기준일을 모르면
주가 칸에 `(기준일 미상)`, 수기 입력값이면 `(수기)` 를 붙인다. 반대로 폴백 소스
표시(「ft 대체」)는 내보내지 않는다 — 값의 신뢰도가 아니라 1차 소스의 건강
상태에 대한 운영 신호라 메일 받는 사람의 판단에 쓸 수 없다.

## 10. 스케줄

- 담당자 출근 08:00 KST → 수집은 **07:40 KST**에 시작해 08:00 전 완료
- Vercel Cron은 UTC이므로 `40 22 * * 0-4` (KST 월~금 07:40)
- 사내 이관 시 동일 시각 crontab에서 `curl -H "x-cron-secret: ..."` 한 줄

## 11. 사내 이관 계획

| 항목 | 1단계 (지금) | 2단계 (사내) |
|---|---|---|
| 저장소 | GitHub | AWS CodeCommit |
| DB | Supabase Postgres | MariaDB |
| 배포 | Vercel (+ 확인용 임시 Render) | 사내 AWS (Next.js standalone) |
| 스케줄 | Vercel Cron | crontab + curl |
| LLM | Gemini Flash (무료) | 유지 또는 온프레미스 모델로 교체 |
| 시세(코스피200 헬스케어) | KRX Open API (무료, `KRX_AUTH_KEY`) | 유지. **이용약관 확인 필요** — 아래 참조 |
| 시세(GSK·Lonza) | LSE·SIX 공식 엔드포인트 (무료, 키 없음) | 유지. 방화벽 허용만 추가하면 된다 |

**애플리케이션 코드는 변경하지 않는다.** 그 목표는 유효하고, 실제로 그렇게 됐다
(Provider 격리와 HTTP 트리거를 택한 이유가 이것이다).

**Render 는 이관 경로가 아니라 곁가지다.** 화면을 잠깐 확인하기 위한 임시
공개 배포이고(`render.yaml`, `docs/render-배포.md`), 무료 플랜에는 크론이 없어
07:40 자동 수집이 돌지 않는다 — 수집은 손으로 트리거하거나 로컬에서 돌린다.
스케줄러를 앱 코드에 넣지 않는다는 §4.1-3 은 그대로다. 확인이 끝나면 내린다.

다만 초안이 적었던 "변경 지점 4곳(`DATABASE_URL`·Prisma `provider`·배포 스크립트·
cron 등록)"은 **DB 쪽이 실제보다 가볍게 적혀 있다.** 구현 후 확인한 사실:
`prisma/migrations/migration_lock.toml` 도 함께 바꿔야 하고, 기존 마이그레이션 8개는
전부 Postgres 방언(`"큰따옴표 식별자"`, `TIMESTAMP(3)`, `DOUBLE PRECISION`,
`"Table_pkey"`)이라 MariaDB 에서 실행되지 않아 **베이스라인 재작성이 필요하다.**
절차는 `docs/운영.md` §3.2 에 있다 — 이관을 계획할 때는 이 절만 믿을 것.

스키마 자체의 이식성은 문제가 없다(enum 미사용, `cuid()` 앱 생성, `@db.Text` 양쪽 호환,
Postgres 전용 구문·확장·`::` 캐스팅·`ILIKE`·배열 타입 없음).

**방화벽 아웃바운드 허용 대상**(전부 HTTPS/443). 전체 목록과 용도는 `docs/운영.md` §3.5에 있다.
`data-dbg.krx.co.kr`(KRX Open API — 코스피200 헬스케어 시세·연초 기준가)에 더해
`api.londonstockexchange.com`(GSK 시세)와 `www.six-group.com`(Lonza 시세)가 추가됐다(§3.2).

**KRX 이용약관 주의.** KRX Open API 약관에는 상업적 이익 추구를 금지하는 조항이 있다.
사내 IR 보고용 내부 활용은 데이터 재판매가 아니지만, **사내 이관 전에 법무·준법 확인을
받아야 한다.** 걸리면 이 1행만 수기 입력으로 되돌리면 된다(`quoteSource = 'manual'` 경로와
검수 화면의 수기 입력란이 그대로 남아 있다).

7. ★ **"운영 시각에 한 번도 돌려 보지 않아서 생긴 결함"** — 이 저장소가 실제로
   당한 종류다. **다음에 같은 것을 찾을 때의 실마리로 남긴다.**

   Task 35(§3.0)의 국내 전일대비 0 결함은 코드를 아무리 읽어도 보이지 않았다.
   장중·장 마감 후에 수집을 돌리면 네이버가 실시간 변동을 주므로 **값이 정상으로
   보였기 때문**이다. 크론 시각(07:40 KST)은 국내장 개장 전이고, 이 세션의 검증은
   한 번도 그 시간대에 이뤄지지 않았다. 결함은 예외 경로가 아니라 **정상 경로에서
   매일 아침** 터지고 있었고, 만들어 내는 값("전 종목 보합")은 완벽하게 그럴듯했다.

   일반화하면: **외부 소스가 주는 "현재" 값은 우리 실행 시각에 의존한다.** 그 소스가
   우리와 같은 시간대에 있고 우리가 그 시장의 개장 전에 돈다면, "오늘"은 아직
   시작조차 하지 않은 상태다. 해외 소스들이 멀쩡했던 것은 실력이 아니라 **시차** 덕이다
   (§3.0 의 소스별 표).

   점검 방법 두 가지:
   - 새 소스를 붙일 때 **실제 크론 시각(07:40 KST)에 한 번 호출해 본다.** 장중 응답만
     보고 판정하지 않는다. 특히 `latest`·`current`·`compareToPrevious…` 처럼 "지금"을
     뜻하는 필드는 개장 전에 무엇을 주는지 반드시 확인한다.
   - 값이 **실행 시각과 무관한지**를 테스트로 고정한다. 같은 응답 픽스처를 서로 다른
     `now` 로 통과시켜 답이 하나인지 본다(`naver.test.ts` 의 불변식 테스트).
     provider 는 `now` 를 인자로 받아야 이 검사가 가능하다.
